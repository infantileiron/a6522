# 自提柜取件提醒 A/B

核对随机分流，判断新提醒能否让更多收件人在三天内取件。

## 业务背景

鹭湾驿投 · 自提柜运营组（模拟）。鹭湾驿投运营约 120 组自提柜。入柜系统按收件人随机分配提醒版本，只纳入实验期内该收件人的首个合格包裹。数据值班员用消息回执、柜门取件记录和客服台账补齐实验台账。分析员在数据齐备后运行复盘，站点负责人据此审批下一批站点的放量。

- 分流台账与消息回执合并后，同一个收件人可能在两组各出现一次。
- 刚入柜的包裹和未送达提醒的记录被随手剔除，导致取件率分母不一致。
- 表格里只有两组取件率，值班员看不到收益的可信范围和投诉风险。

## 演示日流程

1. 09:00 导出鹭湾自提柜提醒实验台账.csv，每行保留一个收件人的首次分配。
2. 09:20 合并通知回执、首个包裹的取件记录及提醒投诉日期。
3. 09:35 导入实验台账，核对分配单号和匿名收件人键是否唯一。
4. 10:00 使用 2026-11-18 零点快照，设置三天取件窗和预设 50% 的 B 组流量。
5. 10:10 核对快照内全量及成熟样本的 A/B 分流，查看仍在等待的分配。
6. 10:20 获取两组取件率、置信区间和投诉护栏，比较住宅、园区、交通站点。
7. 10:40 将放量建议及门槛结果交给站点负责人审批。

CSV 示例为 `鹭湾自提柜提醒实验台账.csv`。批次记录保留 SHA-256 指纹，运行记录保存参数、结果和人工复核决定。更详细的边界条件和样例见 [TOPIC.md](TOPIC.md)。

## 口径与算法

- 按匿名收件人随机，分配单号和收件人键在同一实验台账内各自唯一。A 为原提醒，B 为新版提醒。
- 日期按站点当地自然日。截止日为完整数据覆盖的次日，截止日零点后的分配和事件不可见。分配日记为第 0 天，事件日与分配日之差满足 0 ≤ 日差 < 窗口天数即入窗。
- 分配日到截止日的日差达到窗口天数时进入成熟样本。ITT 在原分组内用全部成熟分配作分母，窗内取件数作分子，提醒未送达的收件人同样计入。提醒投诉率沿用同一口径。
- 取件率双侧检验采用合并比例 p，标准误为 √[p(1−p)(1/nA+1/nB)]，Z 为 B−A 除以标准误。四个期望格频数均达到 5 时报告 p 值。
- 取件和投诉的 B−A 均用两组 Wilson 得分区间按 Newcombe 方法 10 合成双侧置信区间，置信水平为 1−α。
- SRM 在截止前全部分配和成熟分配分别计算 χ²=Σ(O−E)²/E，自由度为 1。E 来自预设 B 组占比。每组期望数至少 5 才能检查，任一检查报警或不可用均暂缓放量。
- 放量需两项 SRM 均通过、取件提升的双侧 p 值小于 α、取件率差置信下界达到实际收益门槛，且投诉率差置信上界不超过容忍上限。
- 组别互换复核：客服标记组别可能填反的分配单后，在同一分配日、同一柜点类型内寻找能翻转放量结论的最少 A/B 互换对。取件与投诉随单走，每单最多用一次，沿用原观察窗与全部门槛。一换一保持各组分配数、成熟数与事件总数不变，SRM 与检验可用性不随互换改变；复核按取件、投诉两个方向求精确最少对数，两百张存疑单也能给出确切结论：要么给出互换方案，要么说明存疑范围内无法翻转。复核记录钉住当时的数据批次，重跑结果一致；迟到记录补齐后导入新批次，可按原圈定范围重算。
- 柜点分层预先记录，以成熟样本展示方向与规模。分层只用于排查和后续实验规划。相同台账与参数可复算。使用事先约定的分析时点和门槛，退还、漏记及迟到回执由上游数据完整性约束。

## 启动

需要 Docker 与 Compose v2。在项目目录执行下面的命令。

```sh
cp -n .env.example .env
docker compose config --quiet
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

前端 `http://127.0.0.1:18262`，FastAPI 文档 `http://127.0.0.1:19262/docs`，数据库 `127.0.0.1:17762`。

| 演示角色 | 账号 | 密码 | 权限 |
|---|---|---|---|
| 复核主管 | `admin` | `admin-demo-2611` | 导入、运行、结果复核、审计。含定时分发时可管理计划 |
| 分析员 | `analyst` | `analyst-demo-2611` | 导入、运行、浏览、导出 |
| 只读查看 | `viewer` | `viewer-demo-2611` | 浏览批次、运行和结果，可导出 |

切换账号请先退出。三个账号由确定性示例脚本创建，重复执行会保留现有账号和批次。

## 实现与本地开发

| 位置或服务 | 职责 |
|---|---|
| `frontend/src` | 原生 HTML/CSS/JS 模块，通过 Nginx ` /api/ ` 代理访问后端。改前端文件后执行 `docker compose up -d --build frontend` |
| `backend/src` | Python 3.11、FastAPI、SQLAlchemy。修改算法后执行 `docker compose up -d --build backend worker` |
| `backend/src/domain` | CSV 字段、可控样本、业务分析和参数元数据 |
| `backend/migrations` | 表结构说明 |
| `worker` | 数据库任务领取、Redis 唤醒、计算、CSV 导出 |
| `db` / `redis` | PostgreSQL 16 / Redis 7 |

`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT` 设定本机端口。`DB_PASSWORD`、`JWT_SECRET` 为运行配置，`SEED_DEMO` 控制启动时生成演示账号和数据。`APP_SUBNET` 设定项目内网，可在地址冲突时调整。共 5 个服务，数据库、Redis 与共享导出使用各自的命名卷。`docker compose down` 停止并保留数据，`docker compose down -v` 同时清除本项目的卷。

前后端共有枚举 `Role`、`Status`、`Review`，分别定义在 `backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js`，用于鉴权、运行状态和复核展示。
